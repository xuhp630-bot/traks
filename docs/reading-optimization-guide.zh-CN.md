# 怎么读埋点数据，以及下一步怎么优化网站

适用站点：Concrete Estimator Hub。后台入口：
[Traks 数据后台](https://traks-selfhost-api.xuhp630.workers.dev)。

**版本要求：本指南适用于包含“Traffic quality & requirements / 优化闭环”的版本。**
若自己的实例暂时找不到这些入口，先核对部署版本，而不是修改流量筛选。
部署、数据接收和历史完整读取需分别验收；新事件不能补回上线前未采集的历史。

## 1. 现在和上线后分别怎么看

1. 登录自己的后台，进入 `concreteestimatorhub.com` 对应站点，先选择日期。
2. 现有概览曲线适合看总体趋势；旧 Events / Paths / Sessions 适合定位单个事件和近期轨迹。
   旧视图有 Top-N、会话/轨迹数量限制，不作为完整导出，更不能默认排除QA流量。
3. 新版上线后，在曲线下方找到 **Traffic quality & requirements**。
4. 日常业务分析选择 **Labelled production**；测试验收选择 **QA**；历史未标记数据选择
   **Historical / unknown**。生产标签不保证是真人或自然搜索用户。
5. 点 **Load complete window**，等到出现 **Complete** 和完整时间范围；不要分析正在读取、
   报错或取消的部分结果。刷新重新取数，不会自动在后台持续扫描。
6. 优先使用过去完整时间窗。Today是当前未结束窗口且有接收延迟，不能直接和完整昨天比较。
   以导出包中的UTC起止范围为准，界面所选“7d”不自动保证是完整7个自然日。

## 2. 每个入口回答什么问题

| 入口               | 主要看什么                                                   | 不应该得出的结论                                       |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------------ |
| 原概览曲线         | 整体访问/事件变化，异常时间段                                | 曲线下降就证明真实用户流失；它仍可能包含QA/unknown     |
| Sessions & export  | 选定流量范围内全部已观测会话摘要，导出CSV                    | 选定窗口以外的完整生命周期；原始无限轨迹               |
| Calculator funnels | 工具访问→有效修改→提交→成功→复制/PDF/报价后续动作            | 把首页搜索、订阅表单、默认值提交、打印请求算进成功     |
| Error requirements | 原因类别、HTTP状态、受影响会话、人工复核与单条需求导出       | 原因类别就是根因；历史错误仍必然复现；HTTP 200就算修好 |
| 优化闭环           | 操作尝试、失败/阻塞/取消、重试、后续成功、无法关联与候选动作 | 重试成功证明同一输入/交易成功，或证明网站修改导致改善  |

操作视图不把同一会话的重复点击当成更多用户。每个分组独立统计，跨页面/操作/问题的会话可能重叠，
不能把各分组数字直接相加当作全站独立用户数。`checkout_success`只代表拿到了结账链接，不是付款完成。
PDF成功只表示下载已发起，不证明用户已保存或打开文件。

关联采用同一collector会话、同一次页面访问、版本、语言、设备、计算器类型/操作，且接收时间必须能证明先后。
相同时间戳、缺少开始/页面标识、重复、并发或跨窗口会进入“无法关联”。这是一种保守信号，不是精确交易级追踪。
同次页面发生重叠尝试后，不再强行解释该操作后续的恢复关系；更精细的并发诊断需要后续显式尝试ID设计。

## 3. 怎么把数据交给我读取

完整读取后默认进入 **优化闭环**，点击：

- **导出聚合分析 JSON** → `website-optimization-evidence.json`
- **导出优化行动单 Markdown** → `website-optimization-actions.md`

把这两个文件上传到当前任务，并告诉我这次希望重点看哪个页面或业务目标，例如：

> 请读取这两个导出文件，先检查时间窗、流量、样本与缺失证据，再按页面/版本/设备分析。
> 输出观察事实、可能原因、反证、待补证据、优先级建议、具体优化动作、验收和上线后观察指标。
> 未经确认不要自动改站或部署，不要把相关性当成因果。

分析包包含当前流量范围的全部聚合分组和候选，不受列表预览条数影响。
界面提供“显示更多操作分组 / 搜索分组 / 优化候选”，可继续展开全部条目。
其他页签中的页面/版本文本筛选不影响它；上层站点筛选仍影响选中的会话范围。
出于隐私，只导出上层筛选键，不导出其原始值，因此比较前后数据时必须在后台重新核对原筛选。
包里不含原始会话/页面ID、搜索原文、输入、报错原文、Cookie、令牌或本机人工复核状态。

不要分享浏览器登录信息或复制完整网络请求头。分析通常不需要会话CSV中的原始会话标识；
优先提供上述聚合包。如果只排查一个问题，也可以在问题卡导出单条需求。

## 4. 从证据到动作

| 观察信号           | 先补什么证据                                              | 可以考虑的修改                                                  | 上线后一起看                                                              |
| ------------------ | --------------------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 工具搜索显示零结果 | 用已知工具名/常用别名和各语言进行QA；没有采集用户搜索原文 | 已有工具标题/别名、搜索规则、无结果替代入口；新工具另做需求研究 | 搜索结果展示会话、零结果/未知结果会话、后续工具使用；不能只优化零结果数字 |
| 校验拒绝较多       | 哪个规则、页面、浏览器；正常/边界输入复现与反证           | 单位说明、示例、范围提示和错误位置，不删除必要校验              | 校验会话、校验后纠正、后续计算成功及未见返回                              |
| 复制失败或反复尝试 | 浏览器权限、安全上下文、嵌入环境与结果存在性              | 适合真实原因的权限提示或手动复制替代路径                        | 尝试、失败、取消、后续成功及无法关联会话                                  |
| PDF/保存/结账错误  | 状态码、业务限制、授权服务端日志、慢网/取消复现           | 修复真实接口/内容问题，或补正确的业务提示、等待/重试入口        | 尝试、成功、失败、业务阻塞、取消、重试；结账链接不是付款                  |
| 尝试后没有返回     | 是否窗口未结束、离开页面、上报丢失、并发或真正卡住        | 证实后再补等待提示、防重复操作或恢复入口                        | 未见返回与无法关联会话，以及真实成功和错误，不能直接称流失                |
| 未知/无法关联较多  | 版本、开始事件、页面标识、接收顺序、诊断上限              | 先修测量口径，不能用猜测回填历史                                | 数据覆盖和可解释性；不要先据此改商业策略                                  |

先保存基线，不要“见到一个数字就改页面”。一次只验证一个主要假设；候选动作需人工确认。
操作记录可以直接填在Markdown行动单：需求链接、负责人、反证、目标页面、具体改动、QA结果、真实上线时间与版本。

## 5. 上线与复查怎么做

1. 在改动前保存JSON/Markdown基线，记录完整UTC时间窗、原筛选、站点、版本、页面、语言、设备和业务目标。
2. 用独立浏览器会话访问站点并加 `?analytics_traffic=qa`。已有查询参数时使用 `&analytics_traffic=qa`。
   QA标记在该活动会话中只提升不降级；结束测试后用新的干净会话访问。不要向生产标签注入假数据。
3. 验证成功、失败、校验、业务阻塞、取消、重复操作和重试，也检查DNT/GPC及敏感内容不被上传。
4. 确认授权后才提交部署；记录实际Git/Worker与埋点标签对应关系。`quality-v1`不是Git SHA，
   后续影响流程/埋点的发布应使用可区分标签并保存发布台账，不能靠部署日期或标签猜版本。
5. 上线当天用QA验证功能与真实接收。之后按相同星期构成、时区、页面、语言、设备、流量、版本口径和筛选，
   比较完整7天窗口；不足以判断时延长到14/28天并标注样本不足，而非保证到某天必然有结论。
6. 主指标之外，同时观察失败、取消、未知、无法关联和采集上限，防止“成功变多只是埋点口径变了”。
7. 满足功能验收可以人工记录“修复已验证”；业务收益是否改善需要独立观察。前后对比不是随机实验，不证明因果。
8. 涉及SEO页面/结构时另外核对GSC页级与查询证据；埋点或部署验证通过不等于排名/收录恢复。

这些按钮提供手动操作和复查窗口，**不会自行创建定时监控、自动需求提交或自动修站**。
定时执行需要另外约定频率、数据读取方式、通知条件和权限；是否已安排，以实际自动化回执为准。

## 6. 技术读取方式

已登录、具有该站点权限的客户端使用：

`GET /api/analytics/:siteId/stats/quality-evidence?period=...&cursor=...`

每一页都校验认证与站点权限。`nextCursor`不为空就继续，必须使用同一时间范围与上层筛选；
到最后一页后核对总组数、事件数和顺序。过期/数据变化/取消时重新开始，不把部分读取称作完整。
Today使用live DO，历史窗口使用R2 SQL；不在来源失败时静默改用短窗口。

推荐直接复用后台的完整读取器与导出按钮，不手工复制Cookie、不把密钥放URL，也不假设站点公开API无需认证。
历史R2 SQL的生产兼容性仍要在经授权发布后验证。本地合成样本只证明集成逻辑，不是真实用户行为证据。

实现与更多边界见 [quality-analysis.md](./quality-analysis.md)。
